##### AUD-020-SEC001 — Low — Unreadable Linux swap inventory suppresses the secret-memory warning

- **Category:** SEC.
- **Severity:** low.
- **Status:** open.
- **Confidence:** high; The exact current helper, extracted unchanged and hash-bound to source, returns zero areas for missing and unreadable synthetic inventories; its caller explicitly returns without warning for zero areas. The independent baseline confirms no alternate inventory warning. Actual host swap leakage was not tested.
- **Release blocking:** false; Low-severity conditional warning omission; this scan is not release acceptance.
- **Affected files and builds:** [src/bin/mhfe/protect.rs](../../src/bin/mhfe/protect.rs) lines 830–833; [src/bin/mhfe/settings.rs](../../src/bin/mhfe/settings.rs) lines 137–141; [src/engine/ffi.rs](../../src/engine/ffi.rs) lines 223–237.
- **Reproduction:** Synthetic missing and directory-valued `proc/swaps` both yield zero areas, identical to a readable header-only inventory; a visible synthetic swap yields one unknown area. The caller's empty-list branch omits the warning before secret input. FFI, rekey/rehearsal and native protection tests do not establish swap confidentiality.
- **Validation assertions:** Exact probe output: missing_inventory=0 known_empty=0 visible_unknown_swap=1 unreadable_inventory=0. Current helper source SHA-256 c8ce24394c08c9afedb605b72c2a1c2208a37093cb0f7a42c5b0a2f0a0977bb8; extracted helper SHA-256 b8193f4df970deb1604c762a85266b807b236e28ccadc6a1e507ceac2af6b566.
- **Expected behavior:** An unreadable swap inventory must be reported as unknown before secrets are read, as SECURITY.md:79–81 promises.
- **Observed behavior:** `unprotected_swap_under()` loses the read-error state by returning `Vec::new()`. `settings::warn_about_swap()` interprets an empty vector as no reportable swap and returns. Existing `unknown` flags cover visible areas with unresolved devices, not failure to read the inventory itself. The Argon2 workspace is intentionally not mlocked, so the documented unknown-encryption warning is the relevant residual-risk control.
- **Impact:** When Linux denies or omits `/proc/swaps`, secret-handling commands silently skip the swap-encryption warning because an inventory read failure is returned as an empty list. On a host with plaintext swap, this removes the warning before the unlocked Argon2 work area is used; paging and later access to the backing storage are additional prerequisites, not demonstrated secret extraction. The code demonstrably omits a promised diagnostic, but exploitation requires an unusual procfs restriction, active plaintext host swap, actual paging and an adversary with access to its storage. No mnemonic/password input can force that environment, and trusted offline-host guidance remains.
- **Prerequisites:** Victim Linux process cannot read `/proc/swaps`. Underlying host uses unencrypted swap, and relevant secret-derived pages actually reach it. Observer can acquire and read the backing storage.
- **Evidence:** Exact source anchors/excerpts and validation limitations are retained in the JSON finding and the hash-bound local semantic review artifact. Executed command evidence, where applicable, is listed above; static proof is not a host-runtime reproduction.
- **Recommended fix:** Represent swap-inventory read failure separately from a confirmed empty inventory and emit an unknown-swap warning before reading secrets; keep existing visible-area classification.
- **Required verification:** Missing, denied and unreadable swap inventories must warn as unknown. A readable header-only inventory must remain a confirmed no-swap case. Existing plaintext, dm-crypt/LVM and zram tests must retain their outcomes.

##### AUD-020-SEC002 — Low — Generated password can reach the main Windows console when VT activation fails

- **Category:** SEC.
- **Severity:** low.
- **Status:** open.
- **Confidence:** medium; Two independent source reviews identify the mismatched preflight and acquired-screen state, and the challenge traces a supported explicit CLI path past every menu refusal. No Windows runtime, failed console API call or scrollback extraction was executed.
- **Release blocking:** false; Conditional Low privacy failure with a source-supported path and unverified Windows runtime prerequisite; this scan is not release acceptance.
- **Affected files and builds:** [src/bin/mhfe/made_password.rs](../../src/bin/mhfe/made_password.rs) lines 210–223; [src/bin/mhfe/terminal.rs](../../src/bin/mhfe/terminal.rs) lines 612–614; [src/bin/mhfe/terminal.rs](../../src/bin/mhfe/terminal.rs) lines 576–581; [src/bin/mhfe/hidden_input.rs](../../src/bin/mhfe/hidden_input.rs) lines 838–845; [src/bin/mhfe/encrypt.rs](../../src/bin/mhfe/encrypt.rs) lines 136–155.
- **Reproduction:** The supported direct invocation is `mhfe encrypt --new-password words --pim 0 --mem 0 --repair-words 0`, followed by a valid 24-word public phrase entered through hidden input. Explicit settings/password/repair options and the 24-word phrase avoid all chooser paths; when Windows VT activation persistently returns false but hidden-input switching succeeds, show writes the password with an inactive guard. This is a source-derived conditional reproduction, not an executed Windows PoC.
- **Validation assertions:** An omitted --repair-words option triggers a chooser whose Windows single_keys refuses failed VT output before password display; this refutes the simpler invocation, not the fully explicit path. The 24-word original avoids a length chooser; alternatively --same-length explicitly handles a short original. HiddenInputCheck tests echo-off input only and is full-tier, so startup does not establish private output capability.
- **Expected behavior:** Generated secret output must require the actual private screen to be active; terminal-handle preflight alone must not authorize printing after Windows VT activation fails.
- **Observed behavior:** can_show_privately checks terminal identity and screen eligibility, while PrivateScreen entry additionally requires control_sequences. A false Windows VT result leaves Flow and PrivateScreen inactive without error. made_password::show then writes the generated secret unconditionally and inactive cleanup never clears that ordinary screen. Refusal gates use the optimistic predicate rather than the acquired privacy state.
- **Impact:** An explicitly requested generated container password is printed even if the private-screen guard cannot activate Windows VT processing. With a valid 24-word original and all menu choices supplied, encryption can reach this display using hidden input while leaving the generated password on the ordinary console. A later reader of retained console output could recover that password; actual Windows failure and retention were not reproduced. This is a conditional local privacy failure, not a protocol-input exploit. It requires a console that is recognized as interactive and supports hidden input but repeatedly fails VT-output activation, then a later observer able to read retained console output. Ordinary Windows VT-capable consoles and Unix do not exhibit the challenged condition; practical host occurrence and scrollback recovery remain untested.
- **Prerequisites:** Windows standard input/output/error are accepted as the same interactive console; TERM is not dumb. Windows output VT processing cannot be enabled on each attempt, while input echo-off switching succeeds. Victim supplies explicit generated-password, PIM, memory and repair-word options and a 24-word original (or explicit --same-length). Main-console output persists and becomes accessible to the later observer; this condition was not tested.
- **Evidence:** Exact source anchors/excerpts and validation limitations are retained in the JSON finding and the hash-bound local semantic review artifact. Executed command evidence, where applicable, is listed above; static proof is not a host-runtime reproduction.
- **Recommended fix:** After acquiring PrivateScreen, refuse to print any generated password unless screen.shows_privately() is true. Align early capability checks with actual VT activation and preserve the final sink guard against capability changes.
- **Required verification:** Inject a console implementation where terminal identity and hidden input succeed but VT activation returns false; explicit generated-password encryption must refuse before secret output. Test the exact direct path with --repair-words 0 and valid 24-word input, as well as the earlier menu refusal. Confirm that actual or enclosing private screens still permit display and clear on exit/cancellation; preserve own-password hidden-input behavior. Exercise words, check-word and chars through the shared display path.
