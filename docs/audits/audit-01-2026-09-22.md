## Scope and methodology

The review traced BIP39 parsing and universal `N→24` packing, truncated-hash
recovery verification, the balanced Feistel schedule, BLAKE2b-256 round salts,
Argon2id invocation, HMAC-SHA-256 masks, inversion, PIM validation, CLI output,
native library contracts, WASM exports, Worker startup/cancellation, build and
release workflows, dependency provenance, published vectors, and user-facing
security claims. It compared implementation constants and byte encodings with
the companion specification and inspected the independent reproduction report
supplied by the project owner; that external script was not retained and is not
counted as independently rerun evidence.

This was an implementation audit of an experimental construction. It was not a
cryptographic proof, professional cryptanalysis, firmware review, side-channel
evaluation, or endorsement for protecting real funds.

## Findings

### AUD-001-SEC001 — Medium — Secret transcript exposure and cleanup

- **Observed:** Early operational result structures exposed detailed plaintext and round transcript material, while several owned buffers had no systematic best-effort cleanup.
- **Impact:** A consumer could retain more sensitive data than required, enlarging the exposure surface in normal errors, serialization, or memory inspection.
- **Remediation:** Operational and vector-only result types were separated; normal APIs omit entropy, packed state, salts, Argon2 keys, masks, and traces. Passwords, engine memory, temporary byte buffers, and result owners use `zeroize`/`Zeroizing` where Rust ownership permits it.
- **Verification:** Source trace, unit tests, WASM contract inspection, and browser API probes.
- **Residual limit:** JavaScript strings, browser/OS copies, allocator behavior, process snapshots, and forced Worker termination cannot be reliably erased.

### AUD-001-API001 — Medium — Offline Worker initialization

- **Observed:** The first Worker design attempted to load its WASM internally, requiring a URL fetch incompatible with embedded single-file consumers enforcing `connect-src 'none'`.
- **Impact:** The intended offline HTML integration could fail or require weakening its network policy.
- **Remediation:** The client now supplies a compiled `WebAssembly.Module` or bytes during an explicit initialization handshake. The Worker performs no fetch and reports readiness before accepting operations.
- **Verification:** Generated-code inspection and Chromium byte/module initialization probes.

### AUD-001-BLD001 — Medium — Native and WASM crate-type collision

- **Observed:** Combining native library and WASM output expectations through the initial crate-type configuration caused clean release integration/link failures.
- **Impact:** A release could pass source review but fail to produce a usable native or browser artifact.
- **Remediation:** Cargo now builds the reusable native `rlib`; the WASM script explicitly requests `cdylib` with `cargo rustc` and then runs binding generation and API verification.
- **Verification:** Locked native build, WASM build, standalone check, and generated API probe passed.

### AUD-001-FUN001 — Low — Fixed-point handling

- **Observed:** The implementation did not enforce the specification's requirement to refuse a rare `Y = X` encrypted result.
- **Impact:** A fixed point would expose the original mnemonic as the apparent container without a warning.
- **Remediation:** Encryption compares input and output states and returns stable error code `FIXED_POINT`; a unit test covers equality and non-equality.
- **Verification:** Unit test and API error mapping passed.

### AUD-001-FUN002 — Medium — Automatic source-length detection

- **Observed:** Recovery APIs required callers to supply `source_words` and tested only that selected layout, although the specification requires testing every 12-, 15-, 18-, and 21-word verifier layout before using the 24-word fallback.
- **Impact:** A container did not carry the promised self-detecting recovery behavior, and callers could not receive the required ambiguity result when multiple short layouts matched.
- **Remediation:** The core now tests every short layout after one inverse permutation. A unique match selects that source length, no match selects 24 words, and two or more matches return `AMBIGUOUS_SOURCE_WORDS` containing the complete list. Rust, CLI, WASM, and Worker APIs expose automatic recovery while retaining explicit length as an override.
- **Verification:** Fast unit tests exercise unique and zero-match outcomes, real packed states for every supported source length, and synthetic two-, three-, and four-match ambiguity cases. The ambiguity test proves that all four current layouts are visited and every match appears in the error.

### AUD-001-API002 — Low — Allocation failure reporting

- **Observed:** Direct allocation of the 512 MiB Argon2 work area could abort the process before the caller received a useful error.
- **Impact:** A constrained UI/Worker could disappear instead of explaining that the suite cannot obtain its required memory.
- **Remediation:** The engine reserves the work area fallibly and returns `MEMORY_ALLOCATION_FAILURE` when reservation fails.
- **Verification:** Source and stable error-contract tests passed. Actual host exhaustion was not induced.

### AUD-001-DOC001 — Low — Forced termination guarantee

- **Observed:** Initial text implied that cancellation by Worker termination executes cleanup and erases the work area.
- **Impact:** Consumers could infer a memory-erasure guarantee browsers do not provide.
- **Remediation:** Documentation distinguishes normal disposal, which reaches Rust cleanup, from forced realm termination, where destructors and physical erasure are not guaranteed.
- **Verification:** README, API, and Worker documentation were inspected for consistent wording.

## Informational observations

- The RustCrypto Argon2 implementation used by the prototype processes its four algorithmic lanes sequentially; this affects speed, not deterministic output.
- The ASCII password helper is exact for its supported subset. Full Unicode 18 NPSS-NFKD must be provided by a pinned conforming implementation and must not use browser-dependent JavaScript normalization.
- The 21-word verifier has a `2^-32` random false-acceptance rate; 24-word sources have no internal verifier. Large recovery searches therefore need known public wallet evidence.
- The repository had no commit or remote, so release provenance, signed tags, and reproducibility across immutable revisions could not be assessed.

## Assessment and limitations

The recorded evidence supports conformance of the implementation to the frozen
experimental suite for the exercised native and Chromium paths. All seven
implementation/documentation findings identified during the review were
remediated in the final source tree. The explicit 21-word corruption tests pass
for both BIP39-checksum-prefix and extra verifier bits, and a literal
cross-platform micro-vector fixes digest-byte and intra-byte bit order.

The result does not establish that the MHFE construction is cryptographically
secure. There is no independent specialist audit, formal proof, constant-time
analysis, hardware-wallet evaluation, full Unicode 18 implementation, Firefox
runtime acceptance, cross-platform release build, reproducible-build comparison,
or induced out-of-memory test. The expensive vector replay and full Chromium
round trip passed before the final cleanup-only and test/documentation edits;
they were deliberately not repeated after the owner requested that no further
long-running checks be performed. The final fingerprint was checked only with
formatting, 17 fast library tests, a WASM library check, and JavaScript syntax checks.
