### Findings

#### AUD-037-FUN001 — Low — An expired request receives a new HTTP response budget

- **Category:** FUN.
- **Status:** Fixed; candidate native CI pending.
- **Release blocking:** Yes, because complete native acceptance is pending.
- **Affected files:** src/bin/mhfe/serve.rs.
- **Reproduction:** Call the real answer function on an accepted loopback socket with Duration::ZERO; the new regression was observed failing before the fix.
- **Expected behavior:** A request-read timeout terminates the connection without further I/O or a fresh response budget.
- **Observed behavior:** The baseline converted every read error into HTTP 400 and returned Ok after writing it; Windows separately failed the existing peer-closure limit.
- **Impact:** An expired public localhost request can enter a second response phase, unlike the standalone Python launcher. Connections remain capped; no secret or remote binding is introduced.
- **Recommended fix:** Return TimedOut or WouldBlock immediately while retaining HTTP 400 for malformed input.
- **Implemented fix:** The match guard preserves the original timeout error; RAII closes both owned socket handles and the serving loop releases its active slot. Tests retain existing timing limits and malformed-input behavior.
- **Required verification:** Deterministic baseline/patched socket control, kernel-read timeout and malformed-response controls, adjacent Rust/Python tests and complete new native CI.

### Variants, caller compatibility and resources

The targeted ripgrep search covers src, packaging, web and scripts. The two Rust read-request matches are the production handler and an in-memory shared-fixture test whose Cursor cannot time out. Python already closes a socket timeout; no second production response-budget variant was found. The request/response budgets, connection cap, public-only 127.0.0.1 binding, headers and checksum admission are unchanged. This changes observable Rust HTTP timeout behavior from 400 to close; it changes no Rust/WASM public API or browser SDK, and wallet-tools was informed.

Microsoft documents that a Winsock receive timeout leaves the connection indeterminate and recommends closing it ([SO_RCVTIMEO](https://learn.microsoft.com/en-us/windows/win32/winsock/sol-socket-socket-options)). The new guard returns the original TimedOut/WouldBlock error before further I/O. Other malformed input keeps its 400 response. RAII closes both owned handles and the existing serving loop decrements its active counter. No startup diagnostic or full-size cryptographic work is added.

The two Rust compilation/test windows were sequential and coordinated with wallet-tools: jobs 1, maximum 1.5 GiB RSS and 3 GiB machine reserve. Other checks were bounded separately; the intermediate Python resource stop is distinguished from a product failure. The companion records each command/source/helper identity and actual peak/reserve observation.
