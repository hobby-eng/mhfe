#### AUD-046-BLD001 — Medium — The Windows CI job does not compile mhfe at 2d1c3ee, so CI and any release fail

- **Status:** fixed.
- **Release blocking:** true.
- **Affected:** src/bin/mhfe/hidden_input.rs:778,780,789,813,835,847,857,868,914; src/bin/mhfe/raw_io.rs:123,130; Cargo.toml:95; .github/workflows/ci.yml:80-104; packaging/Dockerfile.reproducible:97-98
- **Rules:** CORE-43, RUST-02
- **Reproduction:** CI run 41571192819, job portable (windows-2025) 125704207038, step 'Run the fast tests' (cargo test --locked): 11 'error: unreachable `pub` item' in the #[cfg(windows)] mod platform of hidden_input.rs and raw_io.rs; log saved in AUD-046-evidence/c/windows-ci-job.log.
- **Expected:** unreachable_pub = "deny" (added in 4811f6b for AUD-044-ARC021) applied to the Windows modules too; the Windows job reaches 'Check hidden input in a Windows pseudo-console'.
- **Observed:** The Windows platform modules keep `pub` items; only the host target was linted before the push, so cargo test fails on Windows and the Rust ConPTY suite of c1e8113 has never run.
- **Impact:** Release-blocking: release.yml publish needs the ci.yml checks, and the Dockerfile's clippy for x86_64-pc-windows-gnu compiles the same cfg(windows) code, so the canonical build fails too. No secret impact.
- **Recommended fix:** Make the 11 items pub(super) as rustc suggests (pub(crate) where used outside the module), then run cargo clippy --locked --all-targets --target x86_64-pc-windows-gnu -- -D warnings before pushing.

#### AUD-046-BLD002 — Medium — The ConPTY suite starts mhfe without STARTF_USESTDHANDLES, which pywinpty set, so under CI's redirected stdio the tool can bypass the pseudo-console

- **Status:** fixed.
- **Release blocking:** false.
- **Affected:** xtask/src/terminal_windows/conpty.rs:202-225
- **Rules:** RUST-14
- **Reproduction:** Read conpty.rs start(): STARTUPINFOEXW::default() with only cb and lpAttributeList, bInheritHandles 0, EXTENDED_STARTUPINFO_PRESENT \| CREATE_UNICODE_ENVIRONMENT. winpty-rs pty_impl.rs (pywinpty's backend, which the deleted Python suite used and which passed on windows-2025) sets dwFlags = STARTF_USESTDHANDLES with null handles; portable-pty 0.9.0 src/win/psuedocon.rs:116-125 (in the local registry) sets it with INVALID_HANDLE_VALUE because without it 'the spawned process can inherit the explicitly redirected output handles from its parent'. The same flags otherwise.
- **Expected:** mhfe.exe reads and writes the pseudo-console only, whatever xtask's own standard handles are.
- **Observed:** On the GitHub runner xtask's stdout/stderr are pipes; mhfe can get them as its standard handles, see no console on input and write to the CI log, and the first wait_for times out after 20 s. Not run: the Windows job stops earlier (finding above).
- **Impact:** The Windows hidden-input gate of CI and release would fail once the compile error is fixed, or test the wrong handles.
- **Recommended fix:** In start(), set info.StartupInfo.dwFlags = STARTF_USESTDHANDLES (windows_sys::Win32::System::Threading), leaving hStdInput/hStdOutput/hStdError null as winpty-rs does, or INVALID_HANDLE_VALUE as portable-pty does.

#### AUD-046-DOC001 — Medium — The browser documents still say an encryption resolves only after its check has passed and tell the page to call it verified when the promise resolves, but a cancel now resolves it too, to CANCELLED

- **Status:** fixed.
- **Release blocking:** false.
- **Affected:** docs/BROWSER-PACKAGE.md:99, :857-860; web/client.d.ts:478-481; web/client.js:278; docs/API.md:725
- **Rules:** DOC-06, CORE-22
- **Reproduction:** client.encrypt({ phrase, password, passwordRepeat, onUnverified: show, onProgress: ({ stage }) => stage === 'check' && client.cancel() }): onUnverified receives the container, then the promise resolves to CANCELLED. xtask/pages/checks/encrypt.js:365-372 asserts exactly this in both browsers. Then read the lines above.
- **Expected:** DOC-06: the documents state what the code does. Since 9473725 a cancel resolves every long operation to CANCELLED (web/runtime.js:200, :356; web/client.js:826-829), so 'resolved' no longer means 'checked'.
- **Observed:** BROWSER-PACKAGE.md:99 says 'Resolved only after the check has passed'; :858-859 tells the page to say 'verified when the promise resolves' (beside 'not verified on a cancel', which now contradicts it); client.d.ts:478-479 'Resolves only after the container has been decrypted again and checked'; client.js:278 'Resolves only after that check has passed'; API.md:725 'a sealed container, once its check has passed'. The examples at BROWSER-PACKAGE.md:88-125 read the result with no CANCELLED case.
- **Impact:** A host written from the package README marks the container it showed from onUnverified as verified when the user cancels during the check stage, the one presentation the specification forbids for an unchecked container. The d.ts union MhfeSealed \| MhfeCancelled forces a typed host to narrow, which limits the reach; the code is right.
- **Recommended fix:** Wording only, in the five places: 'resolves to the result once the check has passed, or to CANCELLED after cancel()', and in the page duty 'verified when it resolves to the result, not verified when it resolves to CANCELLED or rejects with any other error'.

#### AUD-046-API001 — Low — The owner's length in an onConfirmAgain answer is no longer type-checked, so "15" and [15] are taken as 15 and true reaches the core as 1

- **Status:** fixed.
- **Release blocking:** false.
- **Affected:** web/client.js:1171-1178 (answerConfirmAgain); src/wasm_api/core.rs:1068-1076, :1237-1238 (words: f64); dist/runtime/worker.js:261 (the glue passes words as it is)
- **Rules:** CORE-48, DOC-06
- **Reproduction:** client.rekey({ ..., confirmation: { builtInCheck: true }, words: 15, onConfirmAgain: () => ({ owner: () => true, words: '15' }) }) on a container whose stated 15 words are refused with LENGTH_DIFFERS (ownerLengths [15]). The answer reaches session.confirmAgain(..., '15', ...); the WebAssembly JS API converts an f64 argument with ToNumber, so the core gets 15. The same with words: [15]; with words: true it gets 1.
- **Expected:** BROWSER-PACKAGE.md:498-500 and API.md:951-953: a wrongly typed argument rejects with a TypeError, a length with INVALID_WORD_COUNT; client.d.ts:366-369 types it as WordCount. rekey()'s own words (client.js:611) and onNoLength's { words } (client.js:1148 via describeReference) are checked with requireWordCount.
- **Observed:** de4a350 removed ownerLengths.includes(stated) (AUD-044-ARC006), which also refused every wrong type. Now '15' and [15] confirm the 15-word reading as if 15 had been given, and true is refused with INVALID_REQUEST '... not 1' rather than as a wrongly typed length.
- **Impact:** A page with a type bug in its answer gets a working rekey or a misleading code instead of a refusal; the owner still confirms the shown phrase, so no wrong container results.
- **Recommended fix:** One line in answerConfirmAgain before `stated` is computed: `if (words !== undefined) requireWordCount(words);` (the existing helper). The library still judges membership in ownerLengths.
