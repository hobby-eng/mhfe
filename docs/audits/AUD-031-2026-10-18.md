### Findings

#### AUD-031-API001 — Low — Word-hint requests have no raw utility byte admission

- **Affected:** `src/wasm_api/word_hints.rs:36–45`, `src/word_hints.rs:195–205`, `web/runtime-parts/modules.js:19–21,94–98`, both public module classes.
- **Rules:** CORE-48, CORE-50, CORE-10.
- **Reproduction:** Call raw `wordHints(list, typedUtf8)` and `MhfeWallet.wordHints`/`MhfePasswords.wordHints` with 8,192 and 8,193 raw UTF-8 bytes. Both lists and ASCII/multibyte padding are exercised; literal ordinary hint/completion positives remain correct.
- **Expected:** An outside utility input has an explicit library-owned size domain before avoidable scanning/copying. The existing raw utility bound is a natural shared rule; this is not a new cryptographic-format requirement.
- **Observed:** All supplied bytes are encoded/transferred and accepted beyond that domain; no raw byte admission exists in the traced hint call chain.
- **Impact:** Avoidable linear scanning and transport copies for a small result. No measured exhaustion, remote attack, leak or cryptographic compromise was established. **Release blocking:** false.
- **Recommended fix:** Settle/document the public hint-input contract, use library admission in raw and pre-encode class seams, and expose necessary password-module metadata. Consider native return-type compatibility separately; never silently truncate.
- **Required verification:** Exact/max-plus-one byte and multibyte cases, ordinary literal hints, stable refusal code, and admission before copies/workers.
- **Evidence:** Local `word-hint-boundary-formatted.command.json`; both independent native/browser source traces corroborate the same root, not two findings.

#### AUD-031-UI001 — Low — Invalid UTF-8 in an interactive visible answer bypasses retry

- **Affected:** `src/bin/mhfe/terminal.rs:192–202,479–500`, `check/wallet_reference.rs:350–376`.
- **Rules:** CORE-42, CORE-22.
- **Reproduction:** In actual interactive `check --fingerprint`, submit an ordinary malformed fingerprint and observe a new prompt, then byte `FF` and a line ending.
- **Expected / observed:** Explain the bad interactive answer and ask the same field again; instead a read-time invalid-input error propagates through `?` and ends the CLI with code 2.
- **Impact:** Earlier interactive answers are lost. Scripts are expected to fail fast, and hidden secret input has a separate retry loop; neither is alleged to share this entire defect. **Release blocking:** false.
- **Recommended fix:** Handle this typed invalid-input refusal at the interactive visible-input seam, draining only the refused line while preserving cancellation and genuine I/O failures.
- **Required verification:** Actual PTY retry, later valid input and earlier-state preservation; script, cancel and I/O classifications must remain unchanged.
- **Evidence:** Local `cli-refusal-controls-3` receipts/transcripts; independent native caller challenge.

#### AUD-031-UI002 — Low — An excessive interactive BIP39 passphrase is refused after its prompt

### Optimality assessment and optional opportunities

The structure is generally defensible: independent library owners contain the rules, the front ends translate/sequence them, one native Argon2 work area is reused, ISA selection is cached, secret text has exact-capacity owners, serialization borrows producer data, and native rekey releases old work memory before reserving new memory. Worker isolation, wiping, startup known answers and creation checks are intentional protections, not waste to remove.

The clearest optional resource improvement is the loopback launchers' response copying:

- Native `serve.rs::respond` clones the full page even for HEAD, whose body is not sent; GET then copies it again into the complete response buffer. With the existing 64 MiB/16-connection caps, the static transient payload-copy bound is roughly 2 GiB plus shared data/overhead, not a measured peak.
- The standalone Python launcher similarly builds `head + body` per GET, roughly another page per active response, bounded to about 1 GiB at those caps. Share or stream immutable public page data if this matters, while preserving exact HEAD length, security headers and one total response deadline.
- Native/raw hint paths derive the last-token view for hint and completion separately. After proper input admission, sharing that private calculation is a low-priority simplification, not a measured bottleneck.
- Other optional robustness/lifetime work is an explicit deadline around launcher-test startup reads and earlier release of credentials in a retained ended raw rekey object. Current worker disposal already bounds the supported browser session; no post-end operation, unwiped free or product hang was demonstrated.

The settings error path also queries available memory before filtering unrelated error codes; moving that query inside the relevant branch is minor, optional I/O cleanup. No benchmark, speedup percentage or globally optimal implementation was established. Any profiling remains separate work at unchanged cryptographic settings.
