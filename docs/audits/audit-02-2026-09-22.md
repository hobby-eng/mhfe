## Summary

The implementation conforms to `MHFE-BIP39-256-EXPERIMENTAL-2` on every exercised path. The repository's own ignored replay test passed for all six published vectors in both directions. Three new vectors with non-zero official BIP39 entropies and a synthetic password were generated by the CLI and independently recomputed round by round, forward and inverse, by a separately written Python implementation; every intermediate value matched. The shipped local WASM binary reproduced the published 12-word container under Node.js. Formatting, clippy (native and wasm32), 17 unit tests, `cargo doc`, RustSec audit (61 crates, no advisories), and the release build all passed. No cryptographic, functional, or secret-handling defect was found in the Rust core.

Three low-severity findings are open: the Worker and WASM adapters accept `pim` values of 2^32 and above by silently wrapping them modulo 2^32 (confirmed at runtime); the browser distribution has no automated runtime check of its operational exports and the local build predates automatic length detection; and the security-reporting channel named in `SECURITY.md` is not enabled on the now-published repository, which also does not link the companion specification. Five informational observations are recorded. The earlier `AUD-001` findings remain verified in this source state.

### Findings

#### AUD-002-API001 — Low — Worker and WASM adapters wrap `pim` values of 2^32 and above instead of rejecting them

- **Category:** API.
- **Severity:** low.
- **Status:** open.
- **Release blocking:** false.
- **Affected files and builds:** `web/mhfe-worker.js` lines 13–16 and 26–33 (`requireInteger`, `ensureEngine`); `web/client.js` (`pim = 0` parameters, no bound); generated `dist/wasm/mhfe.js` constructor and `decryptJson` (wasm-bindgen passes JavaScript numbers to `u32`/`usize` parameters through the WebAssembly `i32` conversion, which reduces modulo 2^32).
- **Reproduction:** Under Node.js, `initSync` the distribution and call `new MhfeEngine(2**32)`; read `engine.pim`. Call `new MhfeEngine(2**32 + 31)`. Call `decryptJson(container, 2**32 + 12)` with a staged password.
- **Expected behavior:** Any `pim` outside 0..31 is rejected with `INVALID_PIM`; any `sourceWords` outside {12, 15, 18, 21, 24} is rejected with `INVALID_SOURCE_WORDS`, at every adapter boundary.
- **Observed behavior:** `new MhfeEngine(4294967296)` succeeds and reports `pim = 0`; `new MhfeEngine(4294967327)` succeeds and reports `pim = 31`, `effectivePasses = 384`; `decryptJson(container, 4294967308)` runs as a 12-word recovery. The Worker's `requireInteger` accepts any non-negative safe integer, so `client.encryptAscii(m, p, 2**32)` is forwarded and silently executed at `PIM = 0`. The Worker's `requireSourceWords` does guard the word-count parameter; direct WASM callers are unguarded.
- **Impact:** A caller that passes an out-of-range PIM through arithmetic or a parsing error gets a container at a different work factor without an error. The returned `pim` field reveals the value actually used, so a careful consumer can detect it, and the Rust core itself is correct; this is an adapter contract defect, not a cryptographic one.
- **Evidence:** `mhfe-node-wasm.log` (scratch); generated glue inspection (`wasm.mhfeengine_new(retptr, pim)` with no range check).
- **Recommended fix:** In `web/mhfe-worker.js`, bound `pim` to `0 ≤ pim ≤ maxPim` from `suiteParametersJson()` (or at least `≤ 0xFFFFFFFF`) before constructing the engine and reject otherwise with `INVALID_PIM`; apply the same bound in `web/client.js` for early rejection; document in `API.md` that direct WASM callers must validate integer ranges. Add a Node-based test case for `2**32`.
- **Required verification:** Worker rejects `2**32` and `2**32 + 31` with `INVALID_PIM`; existing PIM 0..31 cases still pass; `verify-wasm-api.mjs` or a new test covers the boundary.

#### AUD-002-BLD001 — Low — Browser operational exports have no automated runtime check; local build is stale

- **Category:** BLD.
- **Severity:** low.
- **Status:** open.
- **Release blocking:** false.

### Informational observations and recommendations

#### AUD-002-SEC001 — Info — Verifier and fixed-point comparisons are not constant-time

`unpack_entropy` (`src/lib.rs` 723) compares the verifier suffix with `!=`, and `reject_fixed_point` (776) compares 32-byte arrays with `==`. Both operate on values the holder of the container can compute for any password guess, so timing leaks nothing beyond the accept/reject outcome that the API already returns, and the 60-second Argon2id schedule dominates any timing signal. No change is required for the threat model; `subtle::ConstantTimeEq` would remove the question if the code is ever reused where the verifier is secret.

#### AUD-002-API002 — Info — Terminating a client before `ready()` is observed leaves an unhandled rejection

`MhfeWorkerClient` creates `#ready` in the constructor and rejects it from `terminate()`, `cancel()`, and the error handlers. If a consumer constructs a client and calls `cancel()` or `terminate()` before awaiting `ready()` or any request, the internal promise rejects with no handler attached and the page logs an `unhandledrejection` event. Attaching a no-op handler (`this.#ready.catch(() => {})`) while still returning the original promise from `ready()` avoids the console noise without changing the contract.

#### AUD-002-FUN001 — Info — Wrong password under automatic detection returns an unverified 24-word result

With a wrong password (or a wrong PIM), `decrypt` without `--source-words` exits 0, prints `Detected source words: 24`, `Recovery verified: false`, and 24 unrelated words. This is exactly the specified fallback: a 24-word source has no in-band verifier, so the format cannot distinguish a wrong password from a genuine 24-word source. The CLI, Rust, WASM, and Worker results all carry the unverified flag (`recovery_verified: false`, `recoveryVerifier: "unavailable"`). Consumers must surface that flag prominently; the CLI could print an explicit warning line on the unverified path. With an explicit `--source-words 12` the same input fails with `RECOVERY_VERIFIER_MISMATCH`, as expected.

#### AUD-002-BLD002 — Info — `actions/checkout` is tag-pinned while the audit action is SHA-pinned

`actions/checkout@v4` appears in all four workflows by mutable tag, whereas `actions-rust-lang/audit` is pinned to a commit SHA. Pinning `checkout` to a SHA (with a version comment, as already done for the audit action) makes the supply-chain posture uniform; Dependabot's `github-actions` ecosystem entry will keep SHA pins updated.

#### AUD-002-DOC002 — Info — README password-guessing table re-derived; figures are correct

All 24 cells of the README table (mean exhaustive-search time `A^L/2 × 84.145 s` for `A ∈ {10, 26, 62}`, `L ∈ {6, 8, …, 20}`) and the stated 2.46× ratio between 84.145 s and 34.26 s were recomputed and match to the printed precision. The false-acceptance table (`2^-128 … 2^-32`, "about 1 in 4.29 billion") is also correct.

- `dist/` is git-ignored and regenerated by CI, so the stale local copy cannot reach a release by itself; the release workflow rebuilds it after `check.sh`.
- The `vectors.yml` path filter omits `src/main.rs` and `src/wasm_api.rs`; this is correct because only the library affects vector output.

### Assessment and limitations

**What the evidence demonstrates.** The Rust core implements the frozen suite exactly: the repository's own replay of the six published vectors passed, three fresh vectors with non-zero entropies were reproduced round by round by an independent implementation in both directions, and the pre-existing WASM binary reproduced the published container under Node.js. Every negative and semantic probe behaved as documented. Static gates, unit tests, documentation build, RustSec audit, and the release build are clean; dependencies are pinned, registry-only, and permissively licensed. Secret-handling code follows the documented best-effort zeroization design, and the operational result types omit all intermediate secrets. The `AUD-001` remediations are intact.

**What remains open.** The three low findings above: integer wrapping of `pim` at the JavaScript/WASM boundary, absence of an automated runtime check for the browser operational exports together with a stale local build, and a security-reporting channel that is named but not enabled, plus the missing specification link.

**What was not tested.** No browser session was run (Chromium or Firefox), so the current Worker source and its automatic-detection path were exercised only by static review and clippy for wasm32; the Node.js probes used the pre-existing, stale WASM binary and not a rebuild. Host out-of-memory behaviour was not induced. No side-channel measurement, no cross-platform build (Windows, macOS, ARM64), no reproducible-build comparison of the CLI or WASM bytes, and no cryptanalysis were performed. The construction's security remains unproven, as the project states, and this record is not a certification.
