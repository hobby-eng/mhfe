Review-only audit of the current mhfe checkout, branch suite-3-c-engine: Rust core, C integration, CLI, wallet rehearsal, WASM/JS, tests/vectors, launchers, documentation, dependency provenance, CI and release scripts. No production changes, commit, push or release. Full-cost vector recomputation and memory-intensive verification excluded by the owner.

Compiled C integration and selected cleanup/thread/error paths were examined; this is not a fresh audit of every upstream implementation.

The audit follows all 32 shared procedure IDs. Negative probes use the actual public library, production terminal/server entry points, and generated browser package where practical. Public fixtures and synthetic data only were used. No full-cost vector calculation or host memory exhaustion was attempted.

### Findings

#### AUD-003-FUN001 — Medium — Hidden terminal input silently removes forbidden password characters

- **Category:** FUN
- **Status:** fixed
- **Release blocking:** true; FUN001 prevents a full-conformance claim
- **Affected files/builds:** src/bin/mhfe/terminal.rs:139; src/password.rs:30; Cargo.lock (rpassword 7.5.4)
- **Reproduction:** Run terminal_input.py against the production CLI. It enters the public zero-12 container, then a password with bytes 61 09 62, 61 00 62, or 61 c2 85 62. It stops before supplying the fingerprint, before memory allocation or Argon2.
- **Expected behavior:** The specification Password encoding section requires rejection of a password containing Cc controls, never cleaning it. The same submitted password must not be silently changed by one adapter.
- **Observed behavior:** All three inputs advance to the Master key fingerprint prompt. rpassword::read_password discards unrecognized controls before Password::new sees the text. The effective password is ab; direct Rust and browser input reject the original strings.
- **Impact:** Interactive encrypt/decrypt/check can operate on a different password from the supplied text. A pasted password can be accepted here and refused by a conforming implementation. The same input helper also reads the separate BIP39 passphrase. No real secret or expensive encryption was used in the reproduction. This blocks a claim of full suite-3 application conformance.
- **Evidence:** local: terminal-input-final.log; exit 1; rpassword-7.5.4/src/lib.rs:98-186; ../mhfe_spec/README.md:205-219
- **Recommended fix:** Use a bounded hidden-input reader that preserves validation-relevant input or reports forbidden characters before filtering. Keep intentional editing keys distinct from submitted or pasted password text; do not trim or clean the password.
- **Required verification:** PTY regressions for TAB, NUL, U+0085 and bracketed paste; matching rejection in stdin, Rust and browser paths; keep backspace, Ctrl+C, normal Unicode and repeat-password interaction usable.

#### AUD-003-FUN002 — Medium — Valid uppercase SegWit addresses are rejected

- **Category:** FUN
- **Status:** verified
- **Release blocking:** false; correction recommended, but no standalone release-blocking claim for this finding
- **Affected files/builds:** src/wallet.rs:103
- **Reproduction:** Run public_api.py. Parse bc1qcr8te4kr609gcawutmrza0j4xv80jy8z306fyu and its all-uppercase spelling through BitcoinAddress::from_str.
- **Expected behavior:** Valid all-uppercase Bech32/Bech32m input must identify the same address; mixed-case input must remain invalid. BIP173 explicitly permits uppercase presentation.
- **Observed behavior:** The lowercase input parses; uppercase returns InvalidAddress("it is not a Bitcoin mainnet or testnet address"). bech32 decodes it, but hrp.as_str() retains uppercase and the subsequent match only accepts bc and tb.
- **Impact:** The rehearsal check rejects a legitimate reference copied from an uppercase QR/address representation. Native and WASM share the parser. Lowercase input is a workaround; no recovered keys are changed.
- **Evidence:** local: public-api-final.log; exit 1; https://github.com/bitcoin/bips/blob/master/bip-0173.mediawiki#uppercaselowercase
- **Recommended fix:** After checksum/case validation, compare the HRP case-insensitively or against the library HRP constants with the appropriate equality semantics. Do not lowercase the entire input before the decoder, which would admit mixed case.
- **Required verification:** Lowercase and uppercase mainnet/testnet P2WPKH and P2TR equality; mixed-case and invalid-checksum rejection; test the public rehearsal entry points.

#### AUD-003-API001 — Medium — The fixed-public-input vector boundary is writable by library consumers

- **Category:** API
- **Status:** verified
- **Release blocking:** false; correction recommended, but no standalone release-blocking claim for this finding
- **Affected files/builds:** src/vectors.rs:225; src/vectors.rs:127
- **Reproduction:** The external consumer public_api.rs takes PUBLIC_INPUTS.into_iter().next().unwrap() into a mutable variable and assigns a different synthetic phrase/password/name. Compilation and validation succeed without invoking Argon2.

- **Status:** fixed

#### AUD-003-SEC001 — Low — Native launcher does not enforce its documented total response deadline

- **Category:** SEC
- **Status:** verified
- **Release blocking:** false; correction recommended, but no standalone release-blocking claim for this finding

- **Reproduction:** Run server_deadline.py on Linux. A fresh production CLI serves an 8 MiB synthetic HTML page. One loopback client sends a valid GET and does not consume the response. Compare the server thread count after 13 seconds.

- **Observed behavior:** The process starts with 2 threads and still has 3 after 13 seconds. set_write_timeout applies to each underlying write, while write_all can return partial progress and start a new timed write. The request-reading path correctly uses an absolute deadline.

### Informational observations and recommendations

#### AUD-003-SEC002 — Zeroization wording exceeds what dependency-owned buffers guarantee

Owned top-level secrets use Zeroizing and C work-area cleanup passes its tests, but NFKD uses an ordinary TinyVec buffer and bip39::to_seed can own a normalized passphrase Cow<String> without zeroization. Immutable browser strings and forced worker/process termination are already acknowledged.

No practical memory extraction was demonstrated. The blanket statement that every Rust buffer is wiped is stronger than the ownership trace supports.

**Recommendation:** Scope the claim to controlled buffers. Normalize the BIP39 passphrase into an explicitly owned wiping buffer and use to_seed_normalized where appropriate; review temporary normalization/formatting buffers before claiming complete coverage.

**Verification:** Source ownership review and bounded synthetic sentinel tests; retain the explicit OS/browser/abort limitations.

**Evidence:** src/password.rs:53; src/wallet.rs:383; API.md (Every buffer...); unicode-normalization 0.1.25 src/decompose.rs; bip39 3.0.0 src/lib.rs:714

#### AUD-003-FUN003 — Rare BIP32 invalid-key paths deserve explicit handling

Master HMAC output is stored without checking for zero or a scalar at least n; public_key then uses expect. An invalid child scalar returns an error instead of the BIP32 next-index rule. The Taproot point-at-infinity case is not explicitly rejected.

Published ordinary vectors pass. No natural mnemonic triggering these astronomically rare cases was found; this is a robustness/formal-completeness recommendation for auxiliary wallet checks, not a reproduced wallet-loss claim.

**Recommendation:** Validate master scalars, return typed errors instead of panics, implement/document child-index retry semantics while retaining the actual derived index, and check Taproot infinity.

**Verification:** Fault-injected HMAC/scalar boundary tests using synthetic values; ordinary published BIP32/BIP49/BIP84/BIP86 vectors must remain unchanged.

**Evidence:** src/wallet.rs:378-479; https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki

#### AUD-003-BLD002 — Parallel vector jobs need serialized checksum publication

Per-file writes and rename are atomic, but write_checksums reads a multi-file snapshot without a shared lock before replacing SHA256SUMS. Two processes can publish snapshots in the reverse order from which they were read.

A parallel run can transiently or finally omit a later file from the manifest; no such defect exists in the reviewed corpus, whose files and verification record match. The full generator was not run in this audit.

**Recommendation:** Serialize manifest scan-and-publish with a shared lock, or publish the complete manifest once after all workers join. Keep atomic per-vector writes and flushes.

**Verification:** A deterministic multi-process interleaving test on small synthetic files, with no Argon2 calls.

**Evidence:** src/bin/mhfe/test_tools.rs:127-167

#### AUD-003-DOC001 — Small documentation inconsistencies remain around password and API boundaries

The vector comment still mentions an embedded NUL though it is now forbidden; the API readPhrase example omits otherLengths; the control-character error says without invisible characters though several format characters remain allowed; the introductory reveals-nothing wording is broader than the later deterministic/equality caveats.

These do not change cryptographic outputs but can confuse consumers or overstate guarantees.

**Recommendation:** Remove the stale NUL reference, document otherLengths and otherDetectedLengths in the API overview, describe exactly the rejected character categories, and qualify the introductory confidentiality claim consistently with the specification.

**Verification:** Documentation/source cross-check; no expensive tests are needed.

**Evidence:** src/vectors.rs:261-263; API.md browser example; src/error.rs ControlCharacterInPassword; README.md introduction

The rare-key recommendation is based on [BIP32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki); no such natural mnemonic was produced. A larger assurance improvement would be to run the retained reduced-cost real-browser checks in CI alongside the existing Node checks, while leaving expensive full vectors in the separately gated workflow.
