### Findings

#### AUD-004-FUN001 — Medium — macOS available-memory estimate counts speculative pages twice

- **Category:** FUN.
- **Status:** fixed (remediation of 2026-10-01; see Remediation and follow-up).
- **Release blocking:** false. Not a demonstrated cryptographic failure or global recovery failure; fix before the next macOS distribution.
- **Affected files and builds:** `src/engine/ffi.rs:331`, `src/engine/native.rs:71`, `src/bin/mhfe/settings.rs`.
- **Reproduction:** Run python3 docs/audits/AUD-004-harnesses/macos-memory.py. It extracts and compiles the unchanged page-summing expression from ffi.rs. The synthetic statistics contain 262144 free pages (including 131072 speculative), 131072 inactive pages, zero purgeable pages and a 4096-byte page size. No Argon2 or large allocation runs.
- **Expected behavior:** Speculative pages must not be added to free_count a second time: Apple XNU explicitly includes them in free_count. This fixture represents 1610612736 bytes in the free-plus-inactive estimate.
- **Observed behavior:** The production arithmetic reports 2147483648 bytes, allowing the 2 GiB default threshold although the non-duplicated estimate is 1.5 GiB. The assertion fails with left 2147483648, right 1610612736.
- **Impact:** On macOS the preliminary resource check can overstate available RAM and admit an operation it should refuse. This raises the risk of memory pressure, swapping or interruption. A native macOS OOM event was not induced; the arithmetic defect, not an actual crash, is demonstrated. Encryption formulas and existing containers are unaffected.
- **Recommended fix:** Remove duplicate accounting of speculative pages and review overlap of the remaining counters against the Apple API contract. Keep the estimator conservative and document that availability is advisory. Consider releasing the Mach host send right and adding a resource margin separately.
- **Required verification:** Add a pure estimator regression using overlapping counters, boundary tests around 2 GiB and non-zero levels, and a macOS integration check. Confirm refusal without allocation when the non-duplicated estimate is below the requested memory.
- **Evidence:** local `AUD-004-evidence/macos-memory.log`, `AUD-004-evidence/apple-contract.log`, `AUD-004-evidence/apple-vm_statistics.h`.
- **Primary reference:** [Apple XNU counter contract](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/mach/vm_statistics.h).

### Informational observations and recommendations

- Promote the bounded real-browser probe into CI: exercise actual workers, both isolation modes, cancellation during execution and immediate restart. Node tests with stand-in workers do not replace this coverage.
- After fixing macOS accounting, consider a conservative memory margin and Linux cgroup-aware limits. /proc/meminfo alone does not establish process/container headroom; successful lazy allocation does not guarantee later pages can be committed.
- Document what happens if application-supplied onProgress/onUnverified callbacks throw, and preferably reject/cancel the client operation explicitly. The raw WASM callback path handles exceptions as cancellation, while page-side event callbacks currently propagate them to the browser event loop.
- The EFF membership/count warning is only a heuristic. Four repeated or deliberately chosen dictionary words should not look equivalent to four independent dice draws; consider an always-visible random-selection reminder and a repetition warning without claiming to measure password entropy.
